# Cluster creation and recovery

Normal startup never runs `initdb`. An empty placement must join or restore the
expected PostgreSQL database. Losing every copy causes an outage requiring
restore, rather than silently replacing the database with an empty one.

## First creation

1. Keep PostgreSQL and the agent stopped on the target volume. Use the same
   image, `APP_NAME`, `PATRONI_SCOPE`, and PostgreSQL credentials that the
   deployment will use. The PGDATA directory must be completely empty.
2. Generate a one-time operator token file, readable only by the operator:

   ```sh
   umask 077
   openssl rand -hex 32 > /path/to/new-cluster-token
   ```

3. Inside the image with the target PGDATA volume mounted, run:

   ```sh
   /app/flux-agent create-cluster \
     --confirm-new-cluster "$APP_NAME" \
     --operator-token-file /path/to/new-cluster-token
   ```

   The command consumes the token before invoking `initdb`, refuses nonempty
   PGDATA, records the database identity, and prints
   `EXPECTED_POSTGRES_SYSTEM_ID=<number>`. A `.consumed` marker prevents token
   reuse. If creation fails, inspect and preserve the partial directory; the
   command never deletes it or automatically retries creation.
4. Retain the printed system ID with the database's recovery records. Optionally
   set it as `EXPECTED_POSTGRES_SYSTEM_ID` on every placement as an independent
   identity constraint. This ENV is not required for existing-volume upgrades
   or replacements joining a verified initialized cluster. Optional
   `CLUSTER_SEED_IPS` retains known peer addresses independently of Flux discovery.
   Start the preinitialized seed and the empty replicas. The seed can rebuild
   etcd around its existing PGDATA; replicas verify the initialized cluster,
   remember its identity, join as learners, and clone that database.

The token is an explicit local operator authorization, not an external consensus
service. It must not be generated by an entrypoint or repeatedly supplied by a
deployment template. Reinitialization of an existing application is a separate
operator decision: preserve the old volumes, provision a separate new cluster,
and deliberately change the deployment identity and application endpoints.

## Existing-cluster upgrade

Before rollout, read `Database system identifier` using the matching image's
`pg_controldata /var/lib/postgresql/data` on surviving copies. Resolve conflicting
IDs before proceeding. No new environment variable is required when upgrading
the existing persistent volumes. `EXPECTED_POSTGRES_SYSTEM_ID` remains an
optional additional constraint. Upgrade one node at a time.
Begin with a healthy existing etcd quorum. If DCS is already lost, first fence
former writers and follow disaster recovery; do not infer old membership from
the current discovery list during migration.

For migration, a node with valid existing PGDATA can derive identity from its own
control file and writes `.flux-agent/cluster.json` inside PGDATA. Empty nodes
may learn an initialized cluster's identity only after linearizable etcd reads
confirm its initialization and registered leader, and an authenticated running
database agrees. New peers return nonce-signed join proofs; legacy TLS peers
are checked using the cluster CA and hostname verification. Unsigned plaintext
legacy responses are never positive trust evidence: upgrade an existing
data-bearing node first so it can provide a signed proof. Conflicting healthy
evidence, missing quorum, corrupt history,
wrong app/scope, and conflicts between deployment, history, and PGDATA block
startup and recovery. The learned identity and known peers are stored in
`/var/lib/etcd/.flux-pg-identity.json`, outside PGDATA so basebackup can clone into
an empty directory; physical clones inherit PGDATA history too. A remembered or
explicit identity cannot be silently replaced. If no data or trustworthy
identity survives, restore is required; empty agreement never authorizes initdb.

`ALLOW_NEW_CLUSTER_BOOTSTRAP`, `ALLOW_ANY_NODE_BOOTSTRAP`, and
`AUTO_BOOTSTRAP_IF_FRESH` remain parseable for compatibility but do not authorize
creation. `ALLOW_PG_DATA_WIPE` no longer authorizes deletion of conflicting data.

## Membership, routing, and replacement

The agent combines current discovery, configured seeds, remembered peers, and
self. A reachable healthy member is retained despite a persistent Flux omission.
Self is never automatically removed. Removing an omitted unreachable member
requires write quorum, a stable discovery view, and repeated direct failures.

etcd startup checks the peer DCS's `/initialize` value against the pinned database
identity before any join or membership mutation. A started registration with
lost local state is removed and re-added as a learner. WAL-only directories are
preserved. Obsolete etcd state is archived under `.flux-etcd-archives` only after
the local etcd process has stopped; updater loops never delete a live WAL.

A rebuilt empty DCS receives a unique cluster token and identity. After verifying
the PostgreSQL pin, each agent restarts its local Patroni client when that DCS
identity changes. This clears cached Raft terms that would otherwise reject a
new control plane whose term is lower than the lost cluster's term. PostgreSQL
identity and data are preserved through that restart.

The proxy requires one healthy primary with the expected system ID. Multiple
primaries, a foreign primary, missing identity, or loss of primary verification
clear the target and close connections to invalidated targets. This protects
connections using the proxy; direct PostgreSQL access bypasses the proxy.
Patroni retains responsibility for leader leases and ordinary failover; the
agent never deletes the leader key because of a failed health probe. A
`pre_promote` guard verifies local PGDATA and DCS identity. Stale `/initialize`
repair uses the pinned identity, a unique running primary, and compare-and-swap.

## Majority loss and disaster recovery

`DEAD_CLUSTER_RECOVERY=false` disables all automatic control-plane rebuilding.
When enabled, rebuilding preserves PostgreSQL identity and requires repeated
agreement from remembered active peers. An unreachable remembered peer blocks
recovery; an incorrect Flux list is not evidence that its old writer stopped.

If former placements really are lost:

1. Fence them: stop the old containers/hosts or otherwise prove they cannot
   accept writes or rejoin. Preserve all recoverable volumes.
2. Set `RETIRED_CLUSTER_IPS=<comma-separated old IPs>` in durable deployment
   configuration for every survivor and replacement, then restart/reconfigure
   those agents. This is an explicit fencing assertion, not a timeout policy.
3. Keep `EXPECTED_POSTGRES_SYSTEM_ID` unchanged. All active peers must agree on
   a safe preserved data authority. A live identity response from a retired
   address contradicts fencing and blocks recovery.
4. If no data copy survives, restore a verified physical backup to one node and
   recover that identity. Logical restores belong in an explicitly created new
   cluster and need a deliberately updated deployment pin.

An epoch file or a system ID alone cannot fence an old primary. This policy
therefore sacrifices automatic minority recovery when former writers cannot
be accounted for. Ordinary quorum-backed Patroni failover remains automatic.

## Backups

Persist both PGDATA and `/var/lib/etcd`. Replication and local dump files do not
protect against deletion of every application volume. Store retained backups
and WAL archives outside Flux's deletion scope and test restores regularly.
The built-in logical backup agent is opt-in, checks the pinned system ID, and
does not itself upload backups or provide immutable retention.
